# 0040. GitHub 조직 horilab 아래에 로봇 레포와 응용 레포를 둔다

- 상태: 채택
- 날짜: 2026-11-23

## 배경

- 이 레포는 로봇을 만들고, 응용(첫 응용은 팔레타이징)은 컨트롤러 API 위에 올라가서 API가 자리 잡으면 다른 레포로 옮길 수 있게 해 두었다 ([0007](0007-repo-structure.md), [0023](0023-robot-controller.md)). 박스 쌓기 뒤에 도전할 주제로 젠가(VLA와 강화학습)가 있다 ([goals.md](../goals.md)).
- 로봇과 응용을 한 프로젝트로 묶어 두려고 GitHub 조직 `horilab`을 만들었다 (2026-11-23). GitHub에는 GitLab의 하위 그룹이 없어서, 조직 아래에 레포가 한 층으로 놓인다.
- 레포는 지금처럼 모두 공개한다.

## 검토한 대안

| 갈래 | 대안 | 장점 | 단점 |
|---|---|---|---|
| 레포 수 | 하나 (응용도 `apps/`에) | API와 응용을 한 커밋에서 같이 고친다 | 응용의 무거운 의존성(젠가의 AI 라이브러리)이 잠금 파일 하나에 묶인다 (0007) |
| | 로봇 하나와, 응용을 모은 레포 하나 | 응용끼리 코드를 나눠 쓰기 쉽다 | 팔레타이징이 젠가의 의존성 버전에 묶인다 |
| | 로봇 하나와 응용마다 하나 | 응용마다 의존성과 바뀌는 속도가 따로다 | 레포를 넘는 바뀜은 판(태그)을 맞춰야 한다 |
| | 더 나눔 (설계와 컨트롤러를 따로, 공통 코드 레포) | 레포마다 작다 | 같은 설계 값에서 나오는 시뮬레이션 모델과 컨트롤러의 팔 치수를 두 레포에서 맞춰야 한다 ([0006](0006-data-and-pipeline.md)). 클라이언트가 컨트롤러 API와 따로 바뀐다 |
| 응용이 가져다 쓰는 법 | git 태그로 설치 (`v0.1.0` 꼴) | 패키지 레지스트리가 없어도 된다. 공개 레포라 설치할 때 로그인이 없다. 레포 안의 한 폴더만 집을 수 있다 | 판을 태그로 직접 붙인다 |
| | PyPI, crates.io에 게시 | 이름만으로 설치한다 | 게시 절차가 늘고, 올린 판은 고칠 수 없다. 아직 바뀌는 API를 공개 저장소에 낸다 |
| | GitHub Packages | GitHub 안에서 끝난다 | Python·Rust 형식을 받지 않는 것으로 안다 (확인하지 않은 기억) |
| 로봇 레포 이름 | `horibot` | 로봇 이름 그대로다. 시뮬레이션 모델 파일도 `horibot.xml`이다 | 이전 프로젝트 레포와 이름이 같다 (주인이 달라 주소는 겹치지 않는다) |
| | `horilab` 그대로 | 할 일이 없다 | 조직과 레포가 같은 이름이라 헷갈린다 |
| | `horilab-robot`처럼 접두사 | 다른 프로젝트 옆에 받아도 구분된다 | 주소에 horilab이 두 번 들어간다 |

## 결정

GitHub 조직 `horilab` 아래에 레포 셋을 둔다. 모두 공개다.

| 레포 | 주소 | 담는 것 |
|---|---|---|
| horibot | github.com/horilab/horibot | 로봇: 부품 설계, 컨트롤러, 펜던트, 서보·카메라 프로그램, 응용이 쓰는 클라이언트, 작업 안내. 지금 이 레포다 |
| palletizing | github.com/horilab/palletizing | 첫 응용: 미니 랜덤 팔레타이징 |
| jenga | github.com/horilab/jenga | 박스 쌓기 뒤의 도전 주제: VLA와 강화학습으로 사람과 젠가 대결 |

- 응용끼리 같이 쓰는 코드를 위한 공통 레포는 미리 두지 않는다. 두 번째 응용이 정말 같이 쓸 때 떼어 낸다.
- 클라이언트는 컨트롤러와 같이 horibot에 둔다. 응용은 horibot의 클라이언트를 git 태그로 설치한다. 패키지 레지스트리는 쓰지 않는다.
- 레포 이름 앞에 `horilab-`을 붙이지 않는다. 코드 이름(Python `horilab_<폴더>`, Rust `horilab-<폴더>`, 0007)은 그대로다.
- PC에서는 작업 폴더 아래에 `horilab/`을 두고, 그 안에 레포 이름대로 받는다: `horilab/horibot`, `horilab/palletizing`, `horilab/jenga`. GitHub의 조직과 레포 꼴을 그대로 따른다.
- 아직 정하지 않은 것(응용 레포를 만드는 때, 시뮬레이션의 자리, 캘리브레이션 같은 책임 나누기, 용어)은 [status.md](../status.md)의 남은 질문에 있다.

## 근거

- 로봇 하나와 응용마다 하나: 젠가는 큰 AI 라이브러리를 쓴다. uv 워크스페이스는 잠금 파일이 하나라서, 같은 레포의 다른 응용도 그 버전에 묶인다 (0007). 0007도 무거운 의존성이 들어오면 다른 레포로 빼기로 했다.
- 로봇 레포를 더 나누지 않는다: 설계 값 하나에서 부품, 시뮬레이션 모델, 컨트롤러의 팔 치수가 같이 나온다 (0006).
- 클라이언트를 horibot에 둔다: 클라이언트는 컨트롤러 API와 늘 같이 바뀐다. 같은 레포면 한 커밋에서 같이 고치고 같이 시험한다. horibot의 태그 하나가 컨트롤러와 클라이언트의 판을 같이 정해서, 둘의 판이 어긋날 일이 준다.
- git 태그로 레포의 한 폴더만 설치하는 것은 uv(git 소스의 `subdirectory`)와 cargo(git 의존성은 레포 안에서 이름으로 크레이트를 찾는다)가 하는 일이다. 두 도구의 문서를 이번에 다시 열어 보지는 않았고, 처음 쓸 때 확인한다.
- 이전 프로젝트는 문서와 말에서 늘 "이전 프로젝트"라고 부르므로 ([CLAUDE.md](../../CLAUDE.md)), 레포 이름이 같아도 가리키는 것이 갈리지 않는다.
- GitHub에서 레포 이름을 바꾸거나 다른 주인에게 옮기면, 옛 주소로 들어오는 웹과 git(clone, fetch, push)을 새 주소로 넘겨 준다. 다만 옛 이름으로 새 레포를 만들면 넘겨주기가 끊긴다. 알고 있는 동작이고 GitHub 문서를 이번에 다시 열어 보지는 않아서, 옮긴 뒤에 옛 주소로 `git fetch`가 되는지 본다.

## 옮기는 순서

실물이 있는 PC에서 먼저 한다 (사용자 결정). 실물이 없는 PC는 그 뒤에 2와 4를 한다.

1. GitHub: `zzingobomi/horilab`의 이름을 `horibot`으로 바꾸고(Settings → General → Repository name), 조직 `horilab`으로 옮긴다(Settings 맨 아래 Danger Zone → Transfer). `gh`로 해도 된다. 조직에 같은 이름의 레포를 미리 만들지 않는다 (옮기기가 막힌다).
2. PC마다: Claude Code와 편집기를 닫고, 레포 밖에서(탐색기 또는 다른 셸) 한다.
   - 받아 둔 폴더를 `<작업 폴더>/horilab/horibot`으로 옮긴다. 예: `D:\study\horilab`이면 이름을 `horibot`으로 바꾸고, 새 `D:\study\horilab` 폴더를 만들어 그 안으로 옮긴다. git에서 뺀 폴더(`records/`, `videos/`, `tools/local/`, `docs-local/` 등)가 같이 옮겨진다.
   - 원격 주소를 바꾼다: `git remote set-url origin https://github.com/horilab/horibot.git`
   - `.venv`를 지우고 `uv sync`로 다시 만든다 (편집 설치가 옛 경로를 가리킨다). Rust의 `target/`은 그대로 두면 cargo가 필요한 만큼 다시 빌드한다.
   - Claude Code의 메모는 사용자 폴더의 `.claude/projects/` 아래, 레포 경로로 이름이 붙은 폴더에 있다 (예: `D:\study\horilab` → `d--study-horilab`). 새 경로에서 Claude Code를 한 번 열어 새 이름의 폴더가 생기면, 옛 폴더의 `memory/`를 그리로 옮긴다.
   - 편집기에서 폴더에 걸어 둔 설정(프로필 연결 등)을 새 경로로 다시 건다.
3. 레포 안에서 옛 이름을 가리키는 곳을 고쳐 커밋한다: CLAUDE.md 첫 줄(horilab은 조직이고 이 레포는 horibot), README 제목, [setup.md](../setup.md)의 레포 받기(새 주소와 2의 폴더 배치), [servo-setup.md](../servo-setup.md)의 받는 주소.
4. 파이처럼 레포를 받아 둔 다른 곳도 원격 주소를 바꾼다. 바꾸기 전에도 넘겨주기로 받고 올리기가 된다.

## 영향

- [0007](0007-repo-structure.md)에서 API가 자리 잡으면 옮길 수 있게 한 응용의 레포는 palletizing과 jenga다.
- 레포를 넘는 일(응용이 쓰는 클라이언트의 판, 응용 레포의 시뮬레이션)은 남은 질문을 정한 뒤 이 기록에 더한다.
