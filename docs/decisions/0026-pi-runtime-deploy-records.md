# 0026. 컨트롤러 파이의 실행 환경, 배포, 기록 넘기기, NAS 쓰임

- 상태: 채택
- 날짜: 2026-11-10

## 배경

- 컨트롤러는 Rust로 짜서 로봇 옆 컨트롤러 파이에서 돌린다. 파이는 로봇을 쓸 때만 켜고, 안 쓸 때는 멀티탭까지 끈다 (7). 파이 배포 명령은 처음 전원부터 컨트롤러 파이에서 돌리려고 그 전에 만들었다 (4, [0034](0034-first-power-tools.md)).
- 시험 기록은 rclone으로 구글 드라이브 `horilab/` 아래에 레포와 같은 경로로 비춘다. 지금까지는 실물이 있는 PC가 올렸다 ([0022](0022-records-and-sync.md)). 컨트롤러가 파이로 가면 기록은 파이에서 생긴다.
- 실물이 있는 PC에서 파이 세 대, NAS, PC, 집 네트워크를 확인하고 패키지를 올렸다 (2026-11-10, [hardware.md](../hardware.md#가진-것)). 그 뒤 [0023](0023-robot-controller.md)의 남은 리서치(파이 컨트롤러, NAS)를 했다. 대안과 자료는 [controller-research.md](../controller-research.md) 5·6절에 있다.

## 결정

1. **OS**: 파이 세 대를 모두 Ubuntu 26.04 LTS로 바꾼다 (hori3 2026-11-15, hori1과 hori2 2026-11-22에 바꿨다).
   - 먼저 부트로더를 올린다. 26.04는 파이 4에 2022-11-25 이후 부트로더를 요구하는데, 가진 세 대는 그보다 옛날이고 22.04 패키지에 든 판으로는 모자란다 ([hardware.md](../hardware.md#가진-것)). 22.04가 도는 채로 라즈베리파이 공식 저장소(raspberrypi/rpi-eeprom)의 파이 4 기본판 이미지를 받아 `rpi-eeprom-update -f`로 올리고, 다시 켠 뒤 `vcgencmd bootloader_version`으로 확인한다 (hori3, 2026-11-15: 2022-01-25 → 2026-10-30판, 설정은 그대로). 카드를 지우기 전에 올라갔는지 볼 수 있다. 안 되면 PC의 Raspberry Pi Imager로 부트로더 이미지를 SD 카드에 써서 한 번 켠다.
   - 여분 파이(hori3)에서 먼저 확인한다. hori3의 SD 카드를 통째 이미지로 떠서 NAS에 둔 뒤, 그 카드로 부트로더를 올리고 26.04를 깐다. 되돌릴 때는 떠 둔 이미지를 다시 쓴다. 확인할 것: 부팅, 어댑터가 `/dev/serial/by-id/` 경로로 잡히는지, 서보 읽기, 재부팅과 전원 차단 뒤 복구(기록을 쓰는 중에 전원을 수십 번 끊어 본다, 7), PC에서 빌드한 실행 파일이 도는지. 이어서 2의 미리 재기를 한다.
   - hori3에 26.04.1(커널 7.0)을 깔았다 (2026-11-15). 공식 이미지를 PC에서 체크섬을 맞춘 뒤 Raspberry Pi Imager의 명령 모드로 썼고, 처음 설정(사용자, SSH 키, 고정 주소, 시간대)은 SD 카드 부팅 영역의 cloud-init 파일(`user-data`, `network-config`)로 넣었다. 처음 켤 때 설정이 오류 없이 들어갔다. 확인할 것 가운데 부팅과, PC에서 빌드한 실행 파일(2의 시험 프로그램, musl 정적 실행 파일)이 도는 것을 봤다. 남은 것(어댑터 경로, 서보 읽기, 전원 차단 뒤 복구)은 컨트롤러 파이(hori1)에서 본다. hori3은 지금 없다 (2026-11-27).
   - 시계: 파이 4는 시계 배터리가 없어서, 다시 켜면 시계가 systemd를 만든 날(이번에는 9월 16일)로 돌아간다. 26.04의 시계 맞추기(chrony)는 인증서로 서버를 확인하는 NTS만 쓰는데, 그 시계로는 서버 인증서가 "아직 유효하지 않다"고 거부해 시계를 끝내 못 맞췄다. 그러면 인터넷 연결(내려받기, 기록 올리기)도 인증서 검사에서 막힌다. chrony에 `nocerttimecheck 1`(시계가 맞기 전 처음 한 번만 인증서 날짜를 보지 않는다)을 넣어 고쳤다 (`/etc/chrony/conf.d/`). 처음 설정 파일에 넣는다.
   - hori1과 hori2도 같은 방법으로 26.04.1을 깔았다 (2026-11-22). 부트로더는 22.04가 도는 채로 2026-10-30판으로 올렸고, SD 카드를 PC로 옮겨 이미지를 쓴 뒤 처음 설정 파일(시계의 `nocerttimecheck` 포함)을 넣었다. 처음 켤 때 설정이 오류 없이 들어갔고 시계도 바로 맞았다. 지우기 전의 22.04 카드는 통째 이미지로 떠 뒀다 (2026-11-10).
   - 막히면 24.04로 간다 (실시간 커널은 Ubuntu Pro로 켜고, 개인 5대까지 무료다).
   - 카메라 파이(hori2)도 26.04로 바꾸고, librealsense는 새 판을 깐다. hori2는 22.04.5에 이전 프로젝트가 소스 빌드한 librealsense 2.57.7이고(2026-11-15 확인), PC의 D405 시험에 쓴 pyrealsense2는 2.59.1이다 (2026-11-14). 새 판이 26.04의 파이 4에서 도는지는 확인하지 않아서 hori3에서 먼저 본다. 26.04를 깐 hori3의 일반 커널에 pyrealsense2를 깔고(PyPI의 공식 ARM 휠이 파이에서 바로 되는지부터 보고, 안 되면 새 판을 소스로 빌드한다), [0031](0031-wiring.md#d405-선)의 D405 남은 확인을 hori3에서 한다. 지연을 재는 동안에는 카메라를 꽂지 않는다. 다 되면 hori2를 같은 방법으로(부트로더부터) 옮기고, 안 되면 hori2는 22.04와 지금 빌드로 쓴다.
     - hori3에서 다 됐다 (2026-11-15). 공식 휠(pyrealsense2 2.59.2)이 uv가 까는 Python 3.12로 바로 돌아서 빌드하지 않는다. librealsense의 장치 규칙 파일(`99-realsense-libusb.rules`)을 `/etc/udev/rules.d/`에 넣어야 일반 사용자로 카메라를 연다. D405 확인은 다 통과했다 ([0031](0031-wiring.md#d405-선)).
     - hori2도 옮겨 같은 휠과 규칙 파일을 넣었다 (2026-11-22). D405가 USB 2.1로 잡히고 컬러와 뎁스 영상이 왔다. 판은 `pyrealsense2==2.59.2.*`로 준다: PyPI의 판 번호가 2.59.2.11152라 `==2.59.2`로는 찾지 못한다.
2. **실시간**: 컨트롤러를 만들기 전에 여분 파이(hori3)에서 미리 잰다. 조정은 하나씩 켜며 잰다: 기본 → 실행 루프 스레드에 실시간 우선순위(SCHED_FIFO)와 mlockall → 코어 3 고정(`isolcpus=3`) → 인터럽트를 0~2번 코어로(`irqaffinity=0-2`) → 클럭 정책 performance. 컨트롤러 파이는 일반 커널에 이 조정을 모두 켜고 쓴다 (26.04에서 기준 안, 미리 재기 2). 실시간 커널(`linux-raspi-realtime`)은 처음부터 켜지 않고, 모자랄 때 고르는 길에 둔다.
   - 미리 재기 (1, 2는 hori3, 3, 4는 hori1):
     1. 26.04를 깐 뒤: 22.04에서 고른 조정을 모두 켜고, 2의 시험 프로그램을 같은 부하로 3시간 다시 돌린다 (결과는 2). 시험 프로그램이 실행 루프의 깨어나는 지연을 직접 재므로 지연 측정 도구(cyclictest)는 따로 돌리지 않는다.
     2. 0024 만드는 순서 1번(Rust 서보 버스, 가짜 서보)이 되면: 가짜 서보 7개(그리퍼 포함)에 첫 연결 때 잰 버스 시간을 넣어, 100 Hz 실행 루프를 흉내 낸 시험 프로그램(`crates/bench`의 `runloop`)을 같은 부하로 몇 시간 돌린다. 22.04(커널 5.15 PREEMPT, 실시간 커널 아님)에서 잰 값(2026-11-12 ~ 13)과 26.04에서 다시 잰 값 (기록은 `records/bench/`):
        - 부하는 stress-ng(CPU 4, 메모리 256 MB, SD에 fsync 쓰기, 입출력)와 iperf3(hori1과 보내기·받기 각 200 Mbit/s)다. 클럭은 늘 1800 MHz였고, 온도는 최고 76.9 °C였으며 클럭 제한은 걸리지 않았다.
        - 보통 스케줄링(SCHED_OTHER) 10분: 깨어나는 지연 최악 36.0 ms, 놓친 박자 164번.
        - SCHED_FIFO 80 + mlockall: 10분 판은 최악 0.47 ms였지만 1시간 판은 최악 2.21 ms였다 (1 ms를 넘은 박자가 36만 박자 중 27개). 놓친 박자는 0번.
        - 여기에 실행 루프를 코어 3에 묶고 인터럽트를 0~2번 코어로 옮긴 2시간 판(`/proc/irq`로 옮김): 99.99%가 0.24 ms(묶기 전 0.90 ms)로 줄었지만, 최악은 1.15 ms로 기준을 넘었다 (72만 박자 중 1개). 놓친 박자는 0번이다. 깨어나는 지연과 일하는 시간의 최악을 더해도 6.1 ms라 한 박자(10 ms) 안이다.
        - 10분 판은 통과해도 몇 시간 판에서 넘으므로, 판정은 몇 시간 판으로만 한다.
        - Ubuntu에 기본으로 켜진 irqbalance가 유선랜 인터럽트 하나를 코어 3에 두었다. 부팅 인자로 `isolcpus=3 irqaffinity=0-2`를 주면 irqbalance도 코어 3을 피한다.
        - 부팅 인자 `isolcpus=3 irqaffinity=0-2`로 코어 3을 떼어 내고 실행 루프를 코어 3에 묶은 3시간 판 (2026-11-12 밤): 깨어나는 지연의 최악은 클럭 정책 ondemand에서 0.23 ms(99.99%는 0.16 ms), performance에서 0.15 ms(0.13 ms)다. 두 판 모두 108만 박자 동안 1 ms를 넘은 박자와 놓친 박자가 없어 통과 기준을 지킨다. 일하는 시간의 최악은 4.2 ms라 깨어나는 지연과 더해도 4.4 ms다. 밤새 코어 3에는 시계 인터럽트와 코어 사이 알림만 왔고, 랜과 SD 카드 인터럽트는 오지 않았다. stress-ng는 코어 3을 쓰지 못해 나머지 세 코어에서 돌았다. 온도는 최고 69.6 °C였고 클럭 제한은 걸리지 않았다.
        - 부하 없는 30분 판은 최악 0.05 ms 안팎이다. 깨어나는 지연의 중간값은 performance 0.008 ms, ondemand 0.022 ms다.
        - 그래서 22.04 일반 커널에서도 SCHED_FIFO 80, mlockall, 코어 3 고정, 부팅 인자 `isolcpus=3 irqaffinity=0-2`로 기준을 지킨다. 클럭 정책은 performance로 한다. 통과에 꼭 필요하지는 않지만 최악과 쉴 때의 지연이 더 짧고, 부하를 건 판에서도 클럭 제한이 걸리지 않았다.
        - 26.04.1(커널 7.0 PREEMPT_DYNAMIC, 실시간 커널 아님)에서 같은 설정과 같은 부하로 잰 3시간 판 (2026-11-15 밤, hori3): 깨어나는 지연의 최악은 0.21 ms(99.99%는 0.15 ms)다. 108만 박자 동안 1 ms를 넘은 박자와 놓친 박자가 없어 통과 기준을 지킨다. 22.04보다 꼬리가 조금 길다 (99%가 0.06 → 0.13 ms, 최악 0.15 → 0.21 ms). 일하는 시간의 최악은 4.2 ms라 더해도 4.4 ms다. 코어 3에는 22.04처럼 시계 인터럽트와 코어 사이 알림만 왔다. 클럭은 늘 1800 MHz였고, 온도는 최고 68.7 °C였으며 클럭 제한은 걸리지 않았다. 부하 없는 30분 판은 최악 0.04 ms, 중간값 0.006 ms다. 그래서 26.04 일반 커널도 같은 설정으로 기준을 지킨다.
     3. 경로 계획을 고르기 전에: 후보(rsruckig, IK)와 충돌 검사(자기 충돌, 안전 평면)의 한 번 계산 시간을 잰다. 고른 계획([0033](0033-planning-and-simulation.md))으로 잰 값 (2026-11-14, hori1, 22.04, 부하 없음, `crates/controller/examples/plan_timing.rs`를 파이용으로 빌드해 돌림):
        - 실행 루프 한 박자 (가짜 서보 여섯의 버스 몫 포함): 중간값은 붙잡기 35 µs, 관절 조그 37 µs, 직교 조그 46 µs이고, 가장 오래 걸린 박자는 0.13 ms다. 직교 조그는 IK 대신 박자마다 야코비안으로 관절 속도를 푼다. 그 몫은 붙잡기와의 차이인 약 11 µs다.
        - 새 이동 명령의 계획: 관절 이동은 중간 0.14 ms(가장 오래 0.27 ms)다. 직선 이동은 30~150 mm의 무작위 직선 30개에서 중간 7.0 ms, 가장 오래 16 ms다.
        - 통과 기준(한 박자 1 ms, 계획 0.1초) 안이다. 부딪힘 검사는 방식을 고르며 따로 쟀다 ([0041](0041-collision-checking.md)).
     4. Rust 버스가 되면: 어댑터를 컨트롤러 파이에 꽂고 서보 7개를 이어 Rust로 버스 왕복 시간을 잰다 (0024 만드는 순서 6번, 처음 전원 날).
   - 통과 기준 (재기 전에 정한다): 부하를 건 채 몇 시간 동안 깨어나는 지연이 최악 1 ms 안, 놓친 박자 0번, 직교 조그의 IK 한 번이 1 ms 안, 새 이동 명령의 계획이 0.1초 안. 부딪힘 검사의 기준은 로봇 설정의 이동 한계에서 끌어냈다 ([0041](0041-collision-checking.md)).
   - 모자라면 이 순서로 고른다: 우리 코드 고치기(계산을 덜 자주, 실행 루프 밖에서) → 실시간 커널(컨트롤러 파이에서 잰다, 근거 2) → 실행 루프 주기 낮추기(100 → 50 Hz) → 그래도 안 되면 파이 5. 파이 5는 예산이 들어 사용자와 정한다.
   - 우선순위는 80에서 시작해 재서 정한다. 99는 커널의 감시 스레드 몫이다.
   - 잴 값: 주기의 평균과 최대, 놓친 박자 수, 계산 시간과 버스 시간(따로), 응답 없음과 다시 보낸 횟수. 컨트롤러 파이에서도 웹 서버, 기록 쓰기, 업로드를 켠 채 몇 시간 잰다.
   - 기록 쓰기와 업로드는 0~2번 코어에서 가장 낮은 우선순위로 돈다. 코어 3을 떼어 줘도 서보 응답을 받아 넘기는 커널 쪽 일은 0~2번 코어에서 돌기 때문이다.
   - 컨트롤러의 실행 명령(`run`)은 리눅스에서 실물 서보에 붙으면 실행 루프 스레드를 코어 3에 묶고 SCHED_FIFO 80을 걸며, 스레드를 띄우기 전에 메모리를 모두 잠근다. 실시간 설정을 걸지 못하면 토크를 켜기 전에 멈춘다 (`--no-realtime`을 주면 보통 스레드로 돈다). 기록은 nice 19 스레드가 코어 3을 피해 메모리 줄(10초 몫)에서 받아 쓴다 (5). 터미널도 따로 스레드가 맡는다. 실시간 함수는 bench와 같은 코드다 (`crates/controller/src/rt.rs`, 2026-11-26).
   - 자가 점검: 실행 명령은 실행 환경(부팅 인자, 커널이 떼어 둔 코어, 클럭 정책, 시각이 맞았는지)과 실행 루프 스레드에 실제로 걸린 정책, 우선순위, 코어를 기록(`meta.json`)에 남기고, 박자마다 깨어나는 지연과 한 박자 일 시간을 `samples.csv`에 남긴다. 끝나면 깨어나는 지연의 최악, 1 ms를 넘은 박자 수, 버린 기록 수를 보인다. `horibot-controller selfcheck`는 판(커밋), 로봇 설정, 실행 환경, 실시간 설정을 시험 스레드에 걸어 본 결과, 서보 어댑터의 고정 경로를 보인다.
3. **빌드**: PC에서 cargo-zigbuild로 `aarch64-unknown-linux-musl` 정적 실행 파일을 만든다.
   - cargo-zigbuild와 zig는 uv 개발 의존성으로 레포 환경에 두고(PC에 따로 깔지 않는다), `uv run tools/pi_build.py`로 부른다.
   - 컨트롤러에는 시스템 C 라이브러리(libudev 등)를 링크하는 크레이트를 넣지 않는다. C 소스를 같이 빌드하는 크레이트(TLS의 ring, aws-lc-rs)는 zig로 빌드돼 정적 실행 파일이 된다 (2026-11-11 확인).
   - glibc판(`aarch64-unknown-linux-gnu.2.35`)은 부하를 건 실행 루프 시험(10분, 2의 미리 재기 2)에서 musl판과 지연 차이가 보이지 않았다. 그래서 musl을 쓴다.
   - 판마다 디버그 정보가 남은 실행 파일도 둔다.
   - 판 내기와 검사는 나중에 GitHub의 무료 arm64 러너로 옮긴다.
4. **배포**:
   - 배포는 `uv run tools/deploy.py`의 `deploy`, `rollback`, `status`로 한다. 처음 설정은 `setup`, 업로드 사용자의 드라이브 로그인은 `login`이다 (처음 전원 전에 만들었다, 2026-11-26. 절차는 [setup.md](../setup.md#9-컨트롤러-파이)).
   - 판마다 `/opt/horilab/releases/<날짜시각>-<커밋>/`에 실행 파일과 그 판의 로봇 설정(`data/robot.toml`)과 시험 순서(`data/scripts/`)를 레포와 같은 자리로 둔다. 임시 폴더에 올려 SHA-256을 맞춰 본 뒤 판 폴더로 옮기고, `current` 링크는 한 번에 바꾼다 (새 링크를 만들어 이름을 바꾼다). 최근 다섯 판과 지금 판만 남긴다.
   - 컨트롤러가 쉬는 상태일 때만 바꾸고, 할 일을 보여 준 뒤 `--yes`를 받는다. 지금은 컨트롤러가 명령으로만 돌아서, 컨트롤러 프로세스가 없을 때만 바꾼다. 새 판이 자가 점검(`selfcheck`)에서 판의 커밋을 답하고 로봇 설정을 읽지 못하면 이전 판으로 되돌린다.
   - 새 판이나 되돌린 판이 켜져도 토크 상태와 서보의 목표를 바꾸지 않고, 움직임은 사람이 다시 명령해야 시작한다 ([0009](0009-control-architecture.md#안전)).
   - 처음 설정은 레포의 스크립트(`pi/controller/setup.sh`)로 한다. 상태만 보기와 넣기가 있고, 여러 번 돌려도 같다.
     - horilab 그룹: 로그인 사용자를 넣는다. 실행 루프의 한도(rtprio 90, memlock 무제한), 판 폴더와 기록 폴더의 쓰기, 기록 올리기를 바로 돌리는 sudo 규칙(`systemctl start horilab-upload.service`만)을 받는다. 서보 어댑터(dialout)와 게임패드(input)도 연다.
     - 업로드 사용자(horilab-upload): dialout과 horilab에 넣지 않는다. 서보 장치도 판 폴더도 쓰지 못한다 (5).
     - 폴더 `/opt/horilab/releases`, `/var/lib/horilab/records`, 부팅 인자(`/boot/firmware/current/cmdline.txt`, 22.04는 `/boot/firmware/cmdline.txt`. 옛 줄은 `.before-horilab`로 남긴다), 켤 때마다 클럭 정책을 performance로 거는 유닛(Ubuntu의 ondemand 유닛이 있으면 막는다), journald 상한 200 MB, rclone, 업로드 유닛과 타이머. 스왑은 있으면 알리기만 한다.
     - 컨트롤러를 늘 켜 두는 systemd 유닛과 그 재시작만 허용하는 sudo 규칙은 컨트롤러가 늘 도는 프로그램(펜던트, [0023](0023-robot-controller.md))이 될 때 더한다. 그때까지는 사람이 SSH로 명령을 돌린다.
   - 파이마다 git pull하고 빌드하지 않는다. NAS, 컨테이너, Ansible은 쓰지 않는다.
   - 컨트롤러를 파이에서 처음 돌릴 때 파이 재부팅 시험을 한다. 부팅 때 저절로 켜진 컨트롤러가 토크와 목표를 바꾸지 않는지, 어댑터를 같은 경로로 다시 찾는지, 시각이 맞기 전에 시작한 기록에 그 표시가 남는지 본다. 저절로 켜지는 컨트롤러는 그 유닛이 생길 때 보고, 처음 설정 뒤에는 다시 켜서 부팅 인자, 클럭 정책, 어댑터 경로, 업로드 타이머를 본다. 서보 쪽 끊김 시험(명령 끊김, 프로그램 다시 켜기, 서보 전원)은 맨 서보 확인에서 한다 ([0028](0028-ur-style-joints.md)의 시험과 측정).
   - hori1에 처음 설정을 넣고 첫 판을 올렸다 (2026-11-27, 서보 없이, [setup.md](../setup.md#9-컨트롤러-파이)대로). `setup --yes`가 할 것 20개를 넣었고, 다시 켠 뒤 `setup`으로 다시 보니 모두 통과였다 (부팅 인자, 클럭 정책 performance, 업로드 타이머가 남았다). 판 `20261127-092543-ad3b775`의 자가 점검은 로봇 설정, 코어 3 떼어 두기, 클럭 정책, 시각, 실시간 설정(메모리 잠금, fifo 80, 코어 3)이 통과였다. 이 자가 점검을 파이의 기록(`records/bench/2026-11-27_092614_selfcheck-hori1`)으로 남겨 업로드를 돌리니 드라이브에 올라갔고, PC에서 받았다. 다시 켠 직후에는 시계가 3시간 넘게 늦었다가 1분 안에 시각 서버에 맞았다. 어댑터 경로는 처음 전원 날 본다.
5. **기록**:
   - 파이는 `/var/lib/horilab/` 아래, 레포와 같은 상대 경로(`records/…`)에 세션 단위로 쓴다 (형식은 [0024](0024-servo-bus.md)). 파이 4에는 RTC가 없어서 시각이 맞았는지도 남긴다.
   - 세션이 끝나면 `meta.json`에 끝난 방식(정상, 보호 정지, 오류)과 끝난 시각을 더한다. 이것이 없으면 중간에 끊긴 세션이다.
   - 실행 루프는 파일에 쓰지 않는다. 기록은 메모리 줄에 넣기만 하고, 다른 코어의 낮은 우선순위 스레드가 모아서 1초쯤마다 쓴다. 줄이 차면 루프는 기다리지 않고 기록을 버리며, 버린 수를 센다.
   - 늘 켜 두는 기록은 메모리 링 버퍼에만 두고, 보호 정지·오류 때 파일로 남긴다. 프로그램 로그는 journald에 상한을 두고 남긴다. SD에 스왑을 두지 않는다.
   - 파이가 systemd 타이머(몇 분마다, 2분 넘게 안 바뀐 파일만: `--min-age 2m`), 시험 끝, 끄기 절차에서 `rclone copy --update`로 드라이브에 올린다. 켤 때는 못 올린 기록부터 올린다. 업로드는 CPU와 디스크를 가장 낮은 우선순위로 쓰고 속도 상한을 둔다. 플래그는 `tools/sync.py`에서 가져와 두 곳에 따로 적지 않는다.
     - 타이머는 켜고 2분 뒤, 그 뒤로는 업로드가 끝난 지 5분마다 돈다. 속도 상한은 초당 2 MB다 (집 업로드 대역을 다 쓰지 않게 둔 어림 값). 업로드 유닛(`pi/controller/horilab-upload.service.in`)의 rclone 인자는 배포 명령이 `tools/sync.py`의 `pi_upload_args`로 채운다. 드라이브 로그인 전에는 돌지 않는다.
     - 드라이브 로그인은 PC의 브라우저로 한다: 배포 명령이 PC의 연결과 같은 앱으로 `rclone authorize`를 돌려 받은 토큰을 파이의 업로드 사용자 설정(권한 600)에 넣는다. 토큰은 PC에 남기지 않는다.
   - 파이에 남은 기록은 드라이브에 같은 파일이 있는지 확인한 세션만, 30일이 지나면 지운다. 남은 공간이 5 GB 아래면 새 기록 세션을 시작하지 않고 알린다. 제어는 그대로 돈다.
   - 업로드는 별도 시스템 사용자로 돌린다. 이 사용자는 서보 장치를 쓰지 못하고(dialout 그룹에 넣지 않는다), rclone 설정은 이 사용자만 읽는다. 파이마다 따로 로그인한다.
6. **NAS**: 배포와 기록의 길목에 두지 않는다. 맡는 일은 넷이다.
   - Cloud Sync로 드라이브 `horilab/`을 "내려받기만, 지우지 않기"로 보관한다. 드라이브가 원본이고 NAS는 사본이다 (NAS 디스크는 하나다).
   - 파이 SD 카드 이미지를 보관한다.
   - 기록을 늘 켜 두기로 정해 드라이브가 모자라면, NAS가 파이에서 끌어와 모두 보관하고 고른 것만 드라이브에 올리는 허브로 바꾼다.
   - 밖에서 집에 들어올 일이 생기면 Tailscale 서브넷 라우터를 맡는다.
7. **켜고 끄기**: 로봇을 쓸 때만 켜고, 안 쓸 때는 멀티탭까지 끈다. 서보 전원도 같이 꺼진다.
   - 끌 때: 끄기 명령(펜던트나 게임패드, 그 전에는 PC에서) → 팔을 쉬는 자세로 옮기고 토크를 끈다 → 기록을 닫고 남은 기록을 올린다(시간 상한을 둔다) → OS를 끈다 → 펜던트에 꺼도 된다고 띄운다 → 서보 전원의 + 플러그를 뺀다 → 멀티탭을 끈다. 쉬는 자세는 토크 없이 팔이 받쳐지는 자세이고, 팔을 설계할 때 정한다.
   - 절차를 잊고 멀티탭을 꺼도 견디게 한다. 기록은 이어 쓰며 1초쯤마다 디스크에 확정하고(5), 못 올린 기록은 다음에 켤 때 올린다. 기록을 쓰는 중에 전원이 끊겨도 SD 카드와 파일 시스템이 견디는지 컨트롤러 파이에서 수십 번 끊어 보고 (처음 전원 뒤, 근거 2), 못 견디면 읽기 전용 루트를 따진다.
   - 켤 때: + 플러그를 뺀 채 멀티탭과 가변 전원을 켜고, 화면에서 12.0 V를 본 뒤 + 플러그를 꽂는다 ([0016](0016-servo-power.md)). 서보는 토크가 꺼진 채 켜진다(메모리 표의 초기값). 컨트롤러는 토크를 켜지 않고 사람의 명령을 기다리며([0009](0009-control-architecture.md#안전)), 시각이 맞기 전의 기록에는 그 표시를 남긴다(5).

## 근거

- 1: 22.04에는 파이용 실시간 커널이 없고 표준 지원이 2027-05에 끝난다. 26.04는 2031-05까지 지원하고, 파이용 실시간 커널을 apt로 무료로 깔며, 파이 4B 인증을 받았다. 24.04는 Pro 등록이 필요하고 지원이 2년 짧다. 여분 파이에서 시험하면 컨트롤러와 카메라 파이는 그대로 두고, 여분 파이는 떠 둔 이미지로 되돌린다. 그래서 카드를 새로 사지 않는다.
  - 카메라 파이: 22.04는 표준 지원이 끝나서 어차피 옮겨야 하고, 세 대가 한 OS면 준비 절차와 배포가 하나다. hori3에는 어차피 26.04를 까니 카메라 시험 때문에 OS를 더 깔지 않고, 그동안 hori2는 지금대로 쓸 수 있다. 옮긴 뒤에 안 되면 떠 둔 SD 이미지로 되돌린다. 컨트롤러 파이에는 카메라가 붙지 않아서, 카메라를 같이 돌리며 잰 지연은 실제와 다르다.
- 2: 다 만든 뒤에 부하가 모자란 것을 알면 고칠 길이 좁다. 파이 자체의 지연, 우리 실행 루프, 계산 시간은 실물이나 완성된 컨트롤러 없이 잴 수 있어서 먼저 잰다. 부하가 있을 때 최악 지연을 줄이는 데는 실시간 우선순위와 코어 격리가 먼저 듣는다는 측정이 있고, 하나씩 켜야 무엇이 들었는지 안다. 일반 커널이 이 조정만으로 기준을 넉넉히 지켜서(26.04에서 최악 0.21 ms) 실시간 커널은 처음부터 켜지 않는다. 실시간 커널은 쓸 일이 생기면 컨트롤러 파이에서 잰다. 망가져도 되는 여분 파이(hori3)에서 먼저 재려 했지만 hori3은 지금 없다 (2026-11-27). 컨트롤러 파이는 SD 카드에 공식 이미지와 처음 설정 파일(1)을 다시 쓰고 배포 명령(`setup`, `login`, `deploy`)을 돌리면 되돌아오므로, 시스템을 크게 바꾸는 시험(실시간 커널, 전원 끊어 보기)도 컨트롤러 파이에서 한다. 지금 재도 그 값으로 정할 것이 없고, 쓸 일이 생겼을 때 재도 품이 같다. 1 ms는 100 Hz 한 박자(10 ms)에서 버스가 쓰는 시간(2.2~5.7 ms, 추정)을 빼고도 남는 값이다.
- 3: 20스레드 PC가 가장 빠르고 Docker가 필요 없다. musl 정적 실행 파일은 OS 판과 상관없이 돈다. glibc판은 같은 도구에서 대상만 바꾸면 되므로 비교 시험을 따로 만들지 않는다. 공개 레포의 arm64 러너는 무료다.
- 4: 실행 파일 하나라 복사와 링크 전환이 가장 단순하고, 되돌리기가 링크 하나다. 설정이 판과 같이 묶여 되돌리기에 설정까지 따라온다. 로봇이 움직이는 중에는 바꾸지 않는다. SHA-256은 끊긴 전송이나 덜 올라간 파일을 잡는다. 재는 동안은 판이 자주 바뀌어 손으로 올려도 충분하다. 프로세스 종료와 재부팅은 복구 길(부팅 순서, 장치 다시 찾기, 시각 맞추기)이 달라 따로 본다.
- 5: PC와 NAS가 꺼져 있어도 기록이 드라이브에 간다.
  - 완료 표시가 있는 세션만 올리면 중간에 끊긴 세션(가장 궁금한 기록)이 올라가지 않는다. 그래서 2분 넘게 안 바뀐 파일을 올리고, 끝난 방식은 `meta.json`으로 가른다.
  - SD는 쓰는 중에 잠깐씩 멈출 수 있다. 실행 루프가 파일을 만지지 않아야 제어 주기가 SD에 매이지 않는다.
  - 양 (어림): 팔 전체를 100 Hz로 다 남겨도 하루 2시간이면 0.5 GB쯤, 1년에 200 GB 안팎이라 64 GB 카드와 쓰기 수명에 여유가 있다. 카드마다 수명이 달라서 확인은 못 했다.
  - 파이에 놓이는 드라이브 토큰은 사용자 분리와 SSH 키로 위험을 줄인다. 업로드 사용자가 서보 장치를 못 쓰면 토큰이 새도 로봇은 움직이지 못한다.
- 6: NAS는 CPU가 2코어라 빌드가 느리고(데스크톱의 약 1/20), 커널 4.4라 arm64 컨테이너를 못 돌린다. 공개 레포의 자체 호스팅 러너는 GitHub가 권하지 않는다. 길목에 끼우면 단계만 늘고 NAS가 꺼질 때 같이 멈춘다.
- 7: 끄는 일이 날마다 있어서 절차로 만든다. 서보 전원이 같이 꺼지면 브레이크 없는 팔이 떨어지므로 쉬는 자세가 먼저다. 절차를 잊는 날도 있으니 갑작스런 전원 끊김에 견디게 하고, 견디는지는 미리 잰다. 업로드 타이머만으로는 끄기 직전의 기록이 남는다.
